## 03 · 数据验收：样例数据不是正式数据集

下载包的合成样例用于检查管线。模板在 split 间重复，分数不能说明泛化。正式提交要求 train≥300、dev≥60、test≥60 条人工审核样例，覆盖三类类别与两种优先级；报告不平衡情况。按真实事件、客户或模板族隔离，测试集在调参前冻结。

去重检查是底线。两句话措辞不同，也可能表达同一个事件；只检查 id 或字符串 hash 不足以防止泄漏。报告至少抽查20对最相似跨 split 样例，说明如何判定。真实客户数据需脱敏并确认使用权限；也可人工编写独立事件集。

## 05 · 评估不是看一条 loss：从逐例输出到混淆矩阵

Teacher forcing 的 NLL 是“给定正确前缀，预测正确下一 token”的能力；任务评估是“给定工单，自由生成整个合法且正确的 JSON”。两者相关但不等价。一个模型可以改善常见标点的概率，却没有改善稀有 urgent 判定。因此验收要保存每条原始生成文本，并在相同解码规则下比较模型。

第一步严格解析JSON，再检查恰好包含 category/priority 两个字段及合法枚举。不要在某一模型上偷偷去除代码围栏、修复括号或增加默认值。若要研究修复器，应把它作为独立系统组件，同时报告原始和修复后结果。

第二步计算 exact match：两个字段都正确才计1。第三步计算类别 macro F1。对类别 c，TP是“真值c且预测c”，FP是“真值非c却预测c”，FN是“真值c却没正确预测c”，包括无效输出。其精确率P=TP/(TP+FP)，召回率R=TP/(TP+FN)，F1可写成：

$$F1_c=\frac{2TP_c}{2TP_c+FP_c+FN_c},\qquad macroF1=\frac1C\sum_{c=1}^{C}F1_c.$$

若分母为0，必须约定处理方式；本项目按固定类别集合计算并记0。正式test要求覆盖所有类别，仍需报告每类支持数。把所有无效输出删除，会人为提高 valid rate 和各类召回；它们必须保留在原分母和对应FN中。

[[LAB:metrics]]

```python
# project/core.py 使用固定类别与严格 schema，下面是单类 F1 的核心
f1 = 2 * tp / (2 * tp + fp + fn) if (2 * tp + fp + fn) else 0.0
macro_f1 = sum(per_class_f1) / len(class_names)
# 无效 JSON 进入其真实类别的 FN；不是“缺失样例”，不能过滤掉
```

accuracy 对每条样例等权，macro F1 对每个类别等权。如果数据以billing为主，一个总是预测billing的模型可能有不错的accuracy，却在account和bug上完全失败。三项主指标要联合看，并补充urgent子集错误，避免用一个平均数遮蔽关键业务代价。

## 06 · 小样本差异：为什么要做配对 bootstrap

两个模型在同一份test上比较，样例难度共享，因此应以样例为单位配对。记录每条新模型和基线的得分，再有放回抽取N个索引；两模型使用同一组索引，重新计算分差。重复B次得到分差的经验分布，可用2.5%和97.5%分位数构造课堂使用的percentile区间。

“有放回”意味着一个样例可以重复出现，也可以没出现。它模拟从经验分布中再次抽样的波动，不等于真的收集了更多数据。独立性假设也很关键：同一客户事件的多个改写有关联时，应该按事件组抽样，而非把所有改写当独立证据。[SciPy 对配对 bootstrap 的定义](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.bootstrap.html)

[[LAB:bootstrap]]

```python
# a,b 是逐例 exact-match 0/1。macro F1 则要每次从重采样的混淆矩阵重算。
rng = np.random.default_rng(42)
deltas = []
for _ in range(2000):
    idx = rng.integers(0, len(a), size=len(a))
    deltas.append(np.mean(b[idx]) - np.mean(a[idx]))
low, high = np.quantile(deltas, [.025, .975])
```

若区间覆盖0，不应把单个正分差宣传为稳定改进；若不覆盖0，也不能自动证明能泛化到新领域。test覆盖、数据泄漏和指标定义仍是更基础的条件。macro F1不是逐例可加指标，不能把每个样例硬算一个F1再套上述均值代码；需要在每次重采样后重算完整指标。

## 07 · 管理代码，也管理实验产物

```text
ticketlab/
  core.py, train.py, evaluate.py, prepare.py
  configs/             # 每次实验的声明配置，进入 Git
  tests/               # 掩码、梯度和重载测试，进入 Git
  data/                # 数据卡 + 合法公开数据/获取脚本
  reports/             # 协议、对比表、错误分析、产物索引
  runs/                # 日志、adapter、checkpoint，不进入普通 Git
```

Git 应能回答三个问题：这次运行用哪版代码、哪版数据和哪份配置。用 `experiment/lora-r8` 等分支保存变化；每个可复现实验保留 commit，交付打 `submission-v1` tag。秘密、私有原始数据、大型权重和虚拟环境不提交。需共享的大产物放对象存储或 Git LFS/DVC，索引记录 SHA256、URI 和权限。README 必须给出从空环境到复现指标的命令。

`adapter/` 是推理/继续适配产物，`training.pt` 才包含继续训练的 optimizer/scaler/RNG。当前代码只支持 epoch 边界恢复。把两者区别写入交付文档，避免“可以重载权重”被误认为“可以精确续跑”。

## 08 · 最终验收：80分且四条硬门槛通过

| 维度 | 分值 | 必须提供的证据 |
|---|---:|---|
| 数据与任务 | 20 | 标签政策、许可/来源、300/60/60+、分组隔离和近重复审计 |
| SFT正确性 | 25 | 测试、token/label对齐、EOS、shift、累积末窗解释 |
| LoRA/QLoRA | 20 | 可训练清单、两种配置、rank消融、真实显存与耗时 |
| 评估 | 20 | 四组逐例结果、三项指标、至少10个错误案例 |
| 复现与管理 | 15 | 固定版本与指纹、环境快照、重载验证、Git tag |

**硬门槛：无已知数据泄漏；无全mask/双shift；基座未被意外更新；adapter能重新加载。** 效果未提升并不自动不及格，缺少证据或隐藏失败才会使结论失效。报告要解释哪个假设被支持，哪个被否定，下一步实验如何区分原因。

最终提交 `reports/report.md`（2–4页）、实验结果与可访问的仓库 tag。完成下方检查清单只记录你的自查，不代表系统已经运行 GPU 或自动评分。


## 09 · 分阶段验收：每一步产物都能单独复核

1. **数学与CPU阶段。** 运行 `python numerical_walkthrough.py` 和原测试套件，提交softmax梯度、LoRA两步梯度、NF4码字表。自己补一个会失败的反例，解释它暴露的契约。
2. **数据与基线阶段。** 提交标签政策、分组划分、数据SHA256，以及未训练的FLOAT/NF4两组逐例输出。此时不调test，不把合成演示数据当正式泛化证据。
3. **训练阶段。** 在相同基座版本和数据上训练LoRA/QLoRA，保存run配置、loss、参数数目、设备、完整step显存与耗时。先使用8–16条过拟合样例检查梯度路径，再回到正式split。
4. **受控消融阶段。** 在dev上比较r=8/α=16与r=16/α=32；记录选择理由。不得仅保留表现最好的seed而隐藏其它已运行结果。
5. **交付阶段。** 冻结代码tag，运行四组最终test，保存逐例文件、汇总指标、配对不确定性分析和至少10个错误案例；在新进程重载adapter并验证输出。

对应的报告至少包括：任务与数据、算法正确性、配置与资源、评估与错误、复现入口。代码片段解释可以写进附录，主报告保持结论与证据清楚。效果没有提升可以诚实交付，但必须能定位是容量、优化、量化、数据还是评估假设需要进一步实验。

**额外验收问题。** 审阅者随机更改一条工单的priority政策，你能指出需要修改的数据契约和评估，而不只是调训练参数吗？审阅者拿走你当前进程，只保留Git tag、数据指纹和adapter，你能恢复推理吗？若要继续训练，是否还具备optimizer、scaler、RNG与进度状态？这些问题比“网页显示完成”更接近真实工程交付。
